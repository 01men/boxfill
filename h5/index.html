＋想先看看复制的是什么？ 
我要用 boxfill 做装柜测算（该用几个柜、运费多少、怎么拼单最省）。

仓库在本地，npm 包名 boxfill，线上工具页是 https://boxfill.ybkkasi.com/app.html （首页是介绍页）。

请按仓库 README.md 完成以下步骤：

1) cd 进仓库，跑 `npm install && npm test`，确认测试全绿（0 失败）再继续。

2) 把 MCP 服务接进你的 MCP 配置（stdio 方式，把路径换成仓库绝对路径）：
   {"mcpServers":{"boxfill":{"command":"node","args":["<仓库绝对路径>/server/stdio.js"]}}}
   装完用 `npm run mcp:probe` 自检一次，它会真起一个 client 连上去把工具调通一遍。
   如果你需要远程或多端共享，改用 `npm run mcp:http`（默认 127.0.0.1:8787/mcp）。

3) 工作流程：
   · 先 list_containers 查柜型库和限重；
   · 再 plan_containers 排柜（这是主入口，几个柜、每柜装了什么、利用率、甩单、违规都在这）；
   · 要钱用 calc_freight；合并订单用 suggest_consolidation；出单据用 gen_docs；
   · 主数据用 upsert_sku 建档或 import_pi 导入 PI/CSV，用 list_skus / list_orders 查询。

4) 必须遵守的约定：
   · 单位锁死 cm / kg / CBM，和 H5 完全一致，不要自己换算成 mm；
   · 柜型写 '20GP' / '40GP' / '40HQ' / '45HQ' / '20OT' / '20FR'，boxType 写 'AUTO' 会自动比选柜型；
   · 运费必须填真实费率（costs.freightPerCbm / thc / doc 等）。费率全 0 时只出装载方案不出钱，
     渠道比价和箱型比选会退化成空表——遇到这种情况先问我要费率，不要编；
   · 限重取四层最小值（箱型上限 / 航线限重 / 船司限重 / 拖车限重）。美线拖车常压到 17.2t，
     比柜型上限低近 10 吨，不取最小值就会算出超重方案；
   · 输入不完整会在入口被挡下并说明缺什么（例如 items[0] 尺寸不完整或非正数），
     看到这类报错是数据问题，不是工具坏了——按提示补齐，不要绕过。

5) 视觉识别（摄像头测尺寸、读电子秤）不在 MCP 里，因为它需要浏览器和 DOM，
   所以只存在于 H5 的「测」屏、由人确认。你要做这类操作时，
   请引导用户打开 https://boxfill.ybkkasi.com/app.html 。

细节（算法原理、10 条硬约束、与 PRD 的偏差、已知限制）都在仓库 README.md 里，
遇到不确定先读它，不要猜。

自己跑的话，两条命令

$npm install&& npm start
→ http://localhost:5173/h5/

H5 端零依赖，只有 MCP 服务端需要 npm install。 另有 npm test（算法测试）、npm run mcp（stdio 服务）、 npm run mcp:probe（MCP 自检）、npm run deploy（部署并端到端验证）。

H5 用的是 ES 模块，浏览器在 file:// 下会拒绝加载模块—— 直接双击一定白屏，必须走静态服务器（npm start 或任意静态服务器）。

给 Agent

工具清单与硬约定

下面是复制指令里那份清单的原样，方便你在别处查阅。

几条会被算错的约定

尺寸单位cm
重量单位kg
体积单位CBM
自动选柜boxType "AUTO"

注意：MCP 侧主数据存在 SQLite（默认 ~/.boxfill/boxfill.db，可用 BOXFILL_DB 覆盖）， H5 侧存在 localStorage，两者是各自独立的主数据，不自动同步。要打通，请在 H5 导出、 服务端用 import_pi 导入。另：node:sqlite 需要 Node ≥ 22.5。

取舍

算得出，还得摆得出来。

放弃理论最优 很多装箱工具给的是悬空塞缝的数学最优。仓管拿着那张图到现场摆不出来—— 图上第二层压在第一层的缝里。我们不做这种方案。
整层铺满，逐层上堆 集装箱只能从门口往里码，物理上本来就是这样。每层铺满、层高定死， 仓管照着摆一定摆得出来，而且每层都能出可直接贴到操作台的俯视图。
拼单不是凑半柜 不是把两个半柜凑成一个柜省一次运费，而是「抛货单 + 重货单」互补， 让体积线和重量线同时吃满。所有柜数都来自真实排布，不是体积除法。
能力

做了哪些事

01 · 装箱

分层码 + 矩形块，不是通用 3D Bin Packing

每层是 2D 矩形块装箱（每个 SKU 在本层摆一个 nx×ny 的规整矩形块），层与层之间简单堆叠。 多起点寻优：体积优先 / 重量优先 / 整除优先 / 混装亲和，四个策略各跑一遍取最优。 朝向按「本层箱数 × 剩余高度还能码几层」预估总收益——层高一旦定死就同时决定了还能往上码几层， 拿到第一个放得下的朝向就用，会白白少装三成。

02 · 约束

10 条硬约束 + 四层限重取最小

门框约束、边长整除、整层码放、重下轻上、堆码上限、单层限高（留 5cm 安全余量）、托盘占用、 混装禁忌、可用容积折扣、配重校验（前后差 ≤800kg、左右差 ≤500kg、CTU 60/50）。 限重取箱型上限 / 航线限重 / 船司限重 / 拖车限重的最小值并在方案里留痕—— 美线拖车常压到 17.2t，比柜型上限低近 10 吨。

03 · 拼单

先硬约束，再多单吸收，最后分账

硬约束按目的港分组，船期兼容交给截关缓冲判断；然后贪心合并 + 多单吸收—— 向已锁定的组继续吸收第三、第四单，只要并入后省的柜数还在增加就继续收。 费用分摊按 max(体积线占用率, 承重线占用率) 计算，尾差记到最后一个成员， 合计严格等于总成本。每条建议带「按此拼单去测算」按钮，一跳到真实排布，建议和执行之间不留断层。

04 · 测量

确认制测量：连续检测 + 人工确认

摄像头逐帧找箱体四边形、持续读秤攒稳定读数，状态灯只报结论 （未找到 / 质量不过关 / 需标定 / 太斜 / 已锁定）。尺寸换算与入库判定全部推迟到用户点「确认测量」之后—— 识别太快把没核对过的数直接弹进主数据，比识别不出来更危险。 秤屏 OCR 是纯 JS 七段数码管字形模板匹配，合成测试识别率 99.7%、误读 0 例：读不出会明确报错，读错不会发生。

05 · 交付

单据、3D 图与离线可用

装箱单 / 装柜清单 / VGM / 配重 / 费用 / A4 打印包一次生成，3D 装柜图支持轴测、分层俯视、 门端侧视、配重剖面。采集与 OCR 全部跑在端侧，断网可测尺寸、读重量、存结果； 主数据、待装清单、方案历史都在 localStorage，断网不丢。存储被禁（无痕模式）时自动退回内存存储，不崩。

FAQ

人们最先问的问题

这个工具到底解决什么问题？＋
三个问题：该用几个柜、运费多少钱、怎么拼单最省。 面向的场景是小商品外贸与仓储——SKU 多、箱规杂、经常有「这票货能不能塞进一个柜还省一次运费」的判断。
为什么视觉识别排在 H5 而不在 MCP 里？＋
摄像头检测和秤屏 OCR 需要逐像素的 ImageData，来自浏览器的 <video> + canvas； MCP 服务端没有摄像头也没有 DOM。所以「测」留在 H5 由人操作，MCP 只开放「算」—— 这既是架构约束，也符合实际：确定性要求最高的一环本来就该由人确认。
为什么首页默认是「算」，不是「测」？＋
摄像头识别依赖受控工位与光线，受环境影响较大；而「算 / 单 / 数」是确定性计算，任何时候都能用。 不把成败押在自动识别上，也是因为识别太快把没核对过的数弹进主数据，比识别不出来更危险。
H5 和 MCP 的数据是同一份吗？＋
算法是同一份，数据不是。H5 用 localStorage，MCP 用 SQLite（默认 ~/.boxfill/boxfill.db）， 两者各自独立、不自动同步。要打通，请在 H5 导出 CSV，服务端用 import_pi 导入。 这条边界是故意的——两个存储层悄悄合并会制造出比不同步更难查的问题。
多个店铺怎么隔离？＋
当前是单库单账本，没有租户隔离。两种做法：每个店铺一个 BOXFILL_DB 文件、各起一个进程（最简单）； 或在 HTTP 前挂带鉴权的反代、按 client 身份分库（需改 http.js 的 session 分发）。 另外 HTTP 服务默认只监听 127.0.0.1 且没有鉴权——任何能访问端口的客户端都能读写全部主数据， 要对外暴露必须自己加鉴权。
算出来运费是 0，为什么？＋
费率没填。费率全 0 时只出装载方案不出钱，渠道比价与箱型比选会退化成空表。 在 H5 里去「数 → 费率设置」填真实费率；在 MCP 里通过 plan_containers / calc_freight 的 costs 传入 freightPerCbm、thc、doc 等参数。
为什么报告的是「柜内占用率」而不是「利用率」？＋
因为理论容积不代表装得满。60×40×35 的箱子装 20GP 只能到 65–70%， 那是箱型不整除柜内尺寸造成的，不是排布差。报相对理论容积的利用率会让人误以为排布算法有问题， 所以界面改为报柜内实际占用率。
还有旧版单箱规计算器吗？＋
有。index.html 是上一代的单箱规装柜计算器（单文件、零依赖、MaxRects 混方向寻优）， 仍在 http://localhost:5173/index.html 提供，可以直接双击打开。 定位不同：它管单箱规的最大装箱数，新 H5 管整票货、多个 SKU、运费与拼单。 注意旧版的 hash 参数单位是 mm，与新 H5 的 cm 不同，两套工具不要混用。
